# Bugs UX – 7 novembre 2026 (branche `fix/ux-search-auto`)

Statut : **investigation seule, aucun code modifié.** Base de tests avant correction : **26 réussis / 0 échec**
(`dotnet test tests\MessageFlow.Tests -c Release`).

Les causes ci-dessous viennent de la lecture du code. Elles n'ont **pas** été observées à l'écran
(l'interface WPF n'a pas été lancée) ; chaque cause est marquée *certaine* (visible dans le code)
ou *hypothèse* (à confirmer par un test).

## Script « Auto fit »

Aucun script Python Auto fit n'existe dans `tools\` ni `docs\` (seuls scripts .py : `tools\Installer\*.py`
et `tools\SourceAccuracyAudit\*.py`, qui contrôlent les données, pas l'affichage).
Le contrôle Auto fit est l'outil C# `tools\VerifyLibraryProjectionFit\Program.cs`. Il mesure chaque
texte de la bibliothèque avec le moteur ET avec la vraie `ProjectWindow` (écrans 1280x720, 1920x1080,
3840x2160 ; DPI 100/125/150 ; A- x6, Auto, A+ x6) : pas de débordement, police >= minimum lisible,
texte des pages identique à l'original, A+ ne dépasse pas le plus grand ajustement, Auto restaure
la taille auto. Il lit la base en lecture seule (`--database`). Non exécuté.

## Bug A – Recherche Bible : Daniel -> Psaumes, la liste revient au début du livre

**Étapes**
1. Onglet Bible. Saisir « Daniel 9 », choisir un verset (ex. 9:24), la liste défile jusqu'à lui.
2. Dans la même boîte de recherche, remplacer par « Psaumes 23 » (ou « Psaumes »).

**Attendu** : la liste affiche Psaumes et se place sur le verset/chapitre demandé (ou garde un point de
repère cohérent).

**Actuel** : la liste repart tout en haut de la nouvelle liste.

**Chemin de code**
- `MainViewModel.ApplyBibleNavigationResult` (MainViewModel.cs ~3598) fait `BibleNavigationItems.Clear()`
  puis `Add()` un par un (jusqu'à 200 éléments) : le `ListBox` remet son défilement à 0 au `Clear()`. *Certaine.*
- Le défilement vers l'élément sélectionné n'est fait que dans `MainWindow.ViewModel_PropertyChanged`
  (MainWindow.xaml.cs:151-163) quand `SelectedBibleNavigationItem` change et n'est pas null, via
  `Dispatcher.BeginInvoke` (priorité Normal). *Certaine.*
- Pour une liste de livres, un chapitre sans verset, ou une recherche sans verset exact,
  `ApplyBibleNavigationResult` met `SelectedBibleNavigationItem = null` (ligne ~3626) : aucun
  `ScrollIntoView` n'est appelé, donc la liste reste en haut. *Certaine.*
- Pour « Psaumes 23:5 » le verset est sélectionné, mais le `BeginInvoke` Normal peut s'exécuter avant
  que le `ListBox` ait généré les conteneurs des ~200 éléments ajoutés un par un
  (`MinHeight=96` par élément, virtualisation) ; `ScrollIntoView` peut alors ne rien faire. *Hypothèse.*
- `MoveBibleNavigationSelection` (MainWindow.xaml.cs:692) appelle `ScrollIntoView` tout de suite : même
  risque, moins visible.

**Piste de correction** : remplacer la liste en une fois (pas de `Clear`+200 `Add`), et défiler après
la mise en page (`DispatcherPriority.Loaded`/`Background`) vers l'élément à afficher (verset demandé,
sinon le chapitre ou le livre correspondant).

## Bug B – Auto fit : texte qui déborde ou n'est pas centré

**Étapes**
1. Ouvrir la fenêtre de projection sur un écran réel (ex. 1920x1080, 125 % DPI).
2. Projeter un paragraphe long (sermon), un verset ou une section de chant ; choisir Auto.
3. Comparer avec la taille de la fenêtre.

**Attendu** : tout le texte est dans la scène, sans coupure, centré verticalement ; chants centrés.

**Actuel (signalé)** : parfois débordement ou texte mal centré.

**Constats dans le code**
- Alignement : `ProjectWindow.xaml.cs:307` met `Center` pour les chants seulement ; sermons et Bible sont
  **alignés à gauche** par conception (le moteur mesure en `Left`). Centrage horizontal inexistant hors
  chants. Centrage vertical : `VerticalAlignment=Center` dans `ParagraphStage`. *Certain ; à confirmer
  avec l'utilisateur si « pas centré » vise ce point.*
- `CalculateLayout` reçoit `dpiScaleX/Y` mais **ne les utilise pas** (`ComputeLayout` ne les prend même pas)
  et la clé du cache (`LayoutKey`) n'en tient pas compte. Aucun effet de DPI dans la mesure. *Certain.*
- Le moteur **estime** la hauteur de l'en-tête, du numéro et de l'indicateur avec des `TextBlock`
  séparés (+8, +16, +12 px forfaitaires) alors que `ProjectWindow` les met dans des lignes de `Grid`
  réelles avec leurs propres marges. Un écart de quelques pixels se paie en bas de page. *Hypothèse.*
- `UpdateProjectionLayout()` utilise `ActualWidth/ActualHeight` de la fenêtre entière puis retranche
  les marges du moteur ; si la fenêtre a une bordure/zone non cliente, la scène réelle est plus petite. *Hypothèse.*
- Tests : `ProjectionAutoFitEngineTests` (10 tests) n'appellent **que le moteur**, avec des tailles fixes
  (1280x720, 1920x1080), et vérifient avec le même `DoesTextFit` que celui qui a produit la mise en page
  (circulaire). Aucun test n'utilise `ProjectWindow` ni le chemin Auto réel (`UpdateProjectionLayout` ->
  `ProjectionFontScaleMultiplier` = 1.0). La vérification réelle existe seulement dans l'outil
  `VerifyLibraryProjectionFit` (hors suite de tests).

**Test à ajouter avant correction** : créer une vraie `ProjectWindow` (voir `Program.cs:265` de l'outil)
à la taille réelle, appeler `UpdateProjectionLayout(w, h)` en Auto (multiplicateur 1.0), puis mesurer
`ParagraphTextBlock` : hauteur/largeur affichées <= `ParagraphStage.ActualHeight/ActualWidth`, et
position verticale centrée (écart haut/bas <= 1 px). Texte d'essai : constantes de test, **pas la base**.

## Bug C – Clics lents ou ignorés ; résultats qui disparaissent et réapparaissent pendant la saisie

**Étapes**
1. Onglet Sermons (ou Bible). Taper une requête de plusieurs lettres, lentement puis vite.
2. Pendant la saisie, cliquer un résultat.

**Attendu** : les résultats précédents restent visibles jusqu'à l'arrivée des nouveaux ; le clic est pris
en compte immédiatement.

**Actuel (signalé)** : la liste se vide puis se remplit ; des clics sont lents ou ignorés.

**Constats dans le code**
- Un debounce existe déjà : Bible 180 ms (`QueueBibleSearch`, ~3349), sermons/chants 250 ms
  (`SearchDebounceMilliseconds`), recherche dans un sermon 220 ms. Le délai est sur un thread du pool,
  puis le travail revient sur le thread UI via `Dispatcher.InvokeAsync`. Il ne faut donc **pas** ajouter un
  deuxième debounce, mais corriger le comportement autour. *Certain.*
- Bible : `UpdateBibleNavigationAsync` s'exécute sur le thread UI (requête EF async, puis
  `ApplyBibleNavigationResult` fait `Clear()` + jusqu'à 200 `Add()` sur le thread UI, chacun déclenchant
  une mise en page). Pendant ce temps les clics attendent : cause des clics lents. *Certain.*
- Disparition/réapparition : (1) `Clear()` avant `Add()` -> la liste est vide un instant ;
  (2) requête vide -> `ClearBibleNavigation` ; (3) `BibleSearchText` est réécrit par le code
  (lignes ~3508, 3536, 3725) ce qui relance une recherche. *Certain pour (1) et (2), hypothèse pour (3).*
- Sermons : la requête DB est dans `Task.Run` (~4094), mais `SetResults` met à jour la liste sur le thread
  UI. Même effet de remplacement brutal.
- `BibleNavigationList_MouseLeftButtonUp` (MainWindow.xaml.cs:727) utilise `ContainerFromElement` ; si la
  liste est remplacée entre l'appui et le relâchement, l'élément visé n'existe plus et le clic est
  silencieusement ignoré (`return`). *Hypothèse plausible pour « clics ignorés ».*

**Proposition (debounce ~200 ms qui garde les anciens résultats)**
- Garder le debounce, aligner Bible/sermons/chants sur 200 ms (constante unique).
- Ne rien vider tant que la nouvelle réponse n'est pas prête : construire la nouvelle liste hors UI et la
  remplacer en une fois ; ne pas appeler `ClearBibleNavigation` pour une saisie transitoire.
- Ignorer les réponses périmées (jeton de version déjà présent : `bibleSearchRequestVersion`).
- Ne pas relancer la recherche quand le code réécrit `BibleSearchText` (drapeau `suppressBibleSearchQueue`
  existe déjà).
